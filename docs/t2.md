# T2. Анализ конвейера «эксперимент → артефакт → страница»

## 1. Постановка задачи

Результат научного эксперимента проходит несколько стадий:

```text
код + данные + параметры
        |
        v
вычисление / запуск ноутбука
        |
        v
артефакты: PNG, HTML, Markdown, CSV, JSON
        |
        v
статический генератор
        |
        v
опубликованная страница
```

В этой работе сравниваются шесть способов переноса результатов на сайт:

1. статические изображения, сохранённые вручную;
2. `nbconvert`;
3. MyST-NB;
4. Quarto;
5. `papermill` с параметризацией;
6. отдельный Python-скрипт, который генерирует Markdown и CSV перед сборкой через `Makefile` или `nox`.

Первые пять пунктов из задания включают несколько вариантов исполнения ноутбуков; последний вариант рассматривается как отдельный производственный конвейер. Основной критерий выбора — не только удобство, но и воспроизводимость: можно ли по опубликованной странице понять, каким кодом, данными и параметрами получен результат.

## 2. Базовый вариант: ручные изображения

### Принцип работы

Исследователь запускает код локально, сохраняет результат, например `figure-1.png`, и вручную добавляет его в `docs/assets/`:

```text
docs/
  experiment.md
  assets/
    figure-1.png
```

В Markdown достаточно написать:

```markdown
![Результат эксперимента](assets/figure-1.png)
```

### Преимущества

- почти не требует инфраструктуры;
- сборка сайта быстрая и предсказуемая;
- размер вычислений не влияет на длительность CI.

### Недостатки

- изображение не содержит доказательства того, какой версией кода и данных оно получено;
- легко забыть обновить картинку после изменения кода;
- численные значения, подписи и таблицы приходится синхронизировать вручную.

Это хороший базовый вариант для сравнения и приемлемый финальный вариант для тяжёлых вычислений, если рядом публикуются метаданные запуска.

## 3. `nbconvert`

`nbconvert` преобразует Jupyter Notebook в HTML, Markdown, LaTeX или другие форматы. Важно различать два режима:

1. **конвертация готового notebook** — код не запускается, а только преобразуется уже сохранённый результат;
2. **execute + convert** — notebook сначала запускается, затем преобразуется.

Пример запуска с выполнением:

```bash
jupyter nbconvert \
  --to html \
  --execute notebooks/experiment.ipynb \
  --ExecutePreprocessor.timeout=600 \
  --output-dir site-generated
```

Для Markdown:

```bash
jupyter nbconvert \
  --to markdown \
  --execute notebooks/experiment.ipynb \
  --ExecutePreprocessor.timeout=600 \
  --output-dir docs/generated
```

### Оценка

`nbconvert` сам по себе не является системой управления экспериментами. Параметры запуска обычно передаются через отдельную подготовку notebook или переменные окружения. Кэширование результатов не является сильной стороной. Повторный запуск обычно выполняет все ячейки снова, если отдельно не организовать кэш.

Для сайта можно публиковать готовый HTML notebook напрямую или конвертировать notebook в Markdown и отдавать его MkDocs/Sphinx. При публикации HTML внутри другого сайта нужно проверить CSS, ссылки на изображения, JavaScript и относительные пути.

## 4. MyST-NB

MyST-NB — расширение экосистемы Sphinx/MyST, которое позволяет включать Jupyter Notebook и executable Markdown в документацию Sphinx. Оно сохраняет сильные стороны Sphinx: директивы, cross-references, builder-ы, API-документацию и темы.

Типовая схема:

```text
.ipynb / .md
    |
    v
MyST-NB + Sphinx
    |
    +--> выполнение ячеек
    +--> кэш выполнения
    +--> HTML / LaTeX / PDF
```

В конфигурации Sphinx обычно задают `myst_nb` среди extensions и выбирают режим выполнения. MyST-NB умеет не запускать notebook, запускать его полностью или использовать сохранённые результаты. Это позволяет отделить сборку документации от обновления вычислительных outputs.

### Сильные стороны

- нативные ссылки на разделы, figures, tables и equations Sphinx;
- возможность использовать `.ipynb` и MyST Markdown в одном проекте;
- кэширование и контроль режима выполнения;
- хорошие возможности для документации Python-кода;
- вывод в HTML и печатные форматы через Sphinx builders.

### Ограничения

- совместимость зависит от версий Sphinx, MyST-NB, Jupyter и execution engine;
- тяжёлые notebooks увеличивают время и память сборки;
- для большого эксперимента желательно предварительно создавать outputs, а не выполнять всё на каждом push.

## 5. Quarto

Quarto — издательская система для научных и технических материалов. Исходником может быть `.qmd` или notebook. Внутри документа размещаются текст, формулы, code cells, параметры, ссылки на figures/tables и citations.

Пример запуска:

```bash
quarto render report.qmd --output-dir site-generated
```

Пример Python-блока с параметрами:

````markdown
```{python}
#| label: fig-result
#| fig-cap: "Результат эксперимента"
#| echo: true

import matplotlib.pyplot as plt
plt.plot([1, 2, 3], [1, 4, 9])
plt.show()
```
````

Ссылку на figure можно написать как `@fig-result`. Quarto также поддерживает citations, figure panels, таблицы из вычислений и экспорт одного исходника в HTML, PDF, Word, ePub или презентацию.

### Сильные стороны

- наиболее естественная модель для воспроизводимых научных отчётов;
- запуск Python, R, Julia и других вычислительных движков;
- cross-references для equations, figures, tables и code listings;
- несколько форматов публикации из одного источника;
- удобное встраивание Plotly, Altair, Bokeh и Jupyter outputs.

### Ограничения

- в CI нужно отдельно устанавливать Quarto, Python/R-пакеты и системные зависимости;
- PDF может потребовать LaTeX или Typst;
- рендер вычисляемого документа может быть значительно тяжелее обычной сборки Markdown;


## 6. `papermill` и параметризованные запуски

`papermill` запускает один и тот же notebook с разными параметрами. Параметры объявляются в специальной `parameters`-ячейке, после чего значения передаются из командной строки:

```bash
papermill \
  notebooks/experiment.ipynb \
  generated/experiment-seed-42.ipynb \
  -p seed 42 \
  -p learning_rate 0.01
```

Для нескольких запусков:

```bash
for seed in 1 2 3 4 5; do
  papermill notebooks/experiment.ipynb \
    "generated/experiment-seed-${seed}.ipynb" \
    -p seed "$seed"
done
```

### Сильные стороны

- параметры эксперимента видны в команде запуска;
- один notebook превращается в серию результатов;
- исходный notebook, executed notebook и параметры можно сохранить вместе;
- удобно запускать матрицу экспериментов в CI или на отдельной машине.

### Ограничения

- `papermill` не решает сам проблему хранения больших данных;
- не является полноценным scheduler и не распределяет задачи без дополнительной системы;
- длительные серии запусков быстро расходуют время CI;
- требуется договориться о схеме имён и метаданных, иначе результаты будет трудно сопоставить.


## 7. Скрипт + `Makefile` или `nox`

Вместо того чтобы заставлять генератор сайта выполнять весь эксперимент, можно сделать явные этапы:

```text
scripts/run_experiment.py
        |
        +--> docs/generated/results.md
        +--> docs/generated/results.csv
        +--> docs/generated/metadata.json
        |
        v
python -m mkdocs build --strict
```

### Вариант с `Makefile`

```make
.PHONY: results site clean

results:
	python scripts/run_experiment.py \
		--data data/input.csv \
		--markdown docs/generated/results.md \
		--csv docs/generated/results.csv \
		--metadata docs/generated/metadata.json

site: results
	python -m mkdocs build --strict

clean:
	rm -rf site docs/generated
```

Запуск:

```bash
make site
```

### Вариант с `nox`

```python
import nox

@nox.session
def site(session):
    session.install("-r", "requirements.txt")
    session.run("python", "scripts/run_experiment.py")
    session.run("python", "-m", "mkdocs", "build", "--strict")
```

### Сильные стороны

- граница между вычислением и публикацией явно видна;
- можно отдельно протестировать скрипт и отдельно собрать сайт;
- Markdown, CSV, JSON и картинки являются обычными артефактами Git/CI;
- можно заменить CI-вычисление загрузкой результатов из хранилища;
- проще контролировать версии кода, данных и окружения.

### Ограничения

- разработчику нужно самостоятельно определить формат outputs;
- графики и таблицы не обновятся, если забыть запустить target `results`;


## 8. Ограничения CI для тяжёлых вычислений

| Ограничение | Практический эффект | Мера контроля |
| --- | --- | --- |
| Лимит минут CI | Длинный notebook или серия `papermill` может исчерпать quota | Таймауты на шаг, профилирование, кэш, перенос вычислений на отдельный runner |
| Таймаут job/step | Зависший процесс блокирует workflow | Явный timeout, checkpoint, сохранение промежуточных результатов |
| Нет GPU или специального ускорителя | CUDA/ROCm-эксперимент не запустится на обычном runner | Self-hosted runner или внешний вычислительный сервис |
| Ограниченная RAM/CPU | OOM, swap и нестабильное время сборки | Уменьшение batch size, предварительное вычисление, отдельная машина |
| Ограниченный кэш | Кэш пакетов и outputs может быть удалён или переполнен | Кэшировать зависимости, но не полагаться на кэш как на единственное хранилище |
| Размер artifact/repository | Большие notebooks, модели и HTML медленно загружаются | Сжимать outputs, хранить данные отдельно, публиковать агрегаты |
| Секреты и доступ к данным | Fork/PR не должен получать закрытые credentials | Разделять build и deploy, использовать Secrets/Environments |
| Нестабильная сеть | Загрузка модели или dataset ломает воспроизводимость | Фиксировать версии, использовать зеркало/registry, проверять checksum |
| Параллельные запуски | Несколько workflow могут перезаписать один результат | `concurrency`, уникальный run id, атомарная публикация |
| Непредсказуемая среда | Обновление Python/пакета меняет результат | Lock-файл, pinned dependencies, container или фиксированный runner |

Конкретные лимиты GitHub Actions зависят от типа аккаунта, runner и настроек организации. Поэтому в проекте нельзя считать CI бесконечным вычислительным кластером. Даже если конкретный запуск проходит, рост числа данных или параметров может сделать pipeline непригодным.

## 9. Граница между двумя стратегиями

### 9.1. Вычисления выполняются в CI

Эту стратегию следует выбирать, если:

- запуск длится недолго и укладывается в установленный timeout;
- зависимости доступны из публичного PyPI/registry;
- данные небольшие, стабильные и не требуют GPU;
- результат должен автоматически обновляться при каждом изменении кода;
- вычисление детерминировано или случайность фиксируется seed;
- failed computation должен блокировать публикацию устаревшей страницы.

Плюс — сильная автоматическая проверка связи «код → результат → сайт». Минус — публикация становится зависимой от времени, ресурсов и состояния внешней CI-среды.

### 9.2. Вычисления выполняются отдельно, CI публикует готовые артефакты

Эта стратегия предпочтительна, если:

- расчёт длится дольше разумного CI timeout;
- нужен GPU, большой объём RAM или закрытая сеть;
- запускается много параметров и нужен scheduler;
- dataset или модель слишком велики для repository/artifact;
- результат должен быть опубликован только после ручной проверки;
- важна стабильная публикация даже при недоступности вычислительной машины.

В этом случае CI проверяет структуру и метаданные, забирает утверждённые outputs из artifact storage или отдельной ветки и собирает сайт. CI не должен молча пересчитывать результат при каждом push.

### 9.3. Практическая граница

Для учебного проекта разумно использовать правило:

```text
если полный pipeline стабильно работает менее 5–10 минут,
не требует GPU и создаёт небольшой output -> можно выполнять в CI;
иначе вычислять отдельно, а в CI публиковать зафиксированный артефакт.
```

Порог не является универсальным лимитом. Это инженерное правило, оставляющее запас на установку зависимостей, очередь runner и повторный запуск.

## 10. Связь результата с кодом и данными

При второй стратегии нельзя публиковать только `figure.png`. Минимальный комплект артефакта должен содержать:

```text
release/experiment-2026-09-22/
  results.md
  results.csv
  figure-01.png
  metadata.json
  environment.txt
```

Пример `metadata.json`:

```json
{
  "experiment": "baseline-classifier",
  "run_id": "2026-09-22T12:00:00Z-42",
  "code": {
    "repository": "https://github.com/L1oneSs/project-python",
    "commit": "<git-commit-sha>",
    "script": "scripts/run_experiment.py"
  },
  "data": {
    "name": "dataset-v3",
    "version": "2026-09-20",
    "sha256": "<dataset-sha256>",
    "source": "<dataset-url-or-storage-id>"
  },
  "parameters": {
    "seed": 42,
    "test_size": 0.2
  },
  "environment": {
    "python": "3.13.5",
    "platform": "linux-x86_64",
    "requirements_sha256": "<lock-file-sha256>"
  },
  "outputs": {
    "results_csv_sha256": "<output-sha256>",
    "figure_sha256": "<figure-sha256>"
  },
  "created_at": "2026-09-22T12:05:00Z"
}
```

В самой опубликованной странице нужно показывать хотя бы:

- короткий `run_id`;
- commit SHA или ссылку на commit;
- название и версию dataset;
- параметры запуска и random seed;
- дату и версию окружения;
- ссылку на исходный notebook/script;
- checksum или ссылку на полный metadata-файл.

### Защита от несогласованных артефактов

Перед публикацией полезно выполнить проверки:

```bash
test -f docs/generated/results.md
test -f docs/generated/results.csv
test -f docs/generated/metadata.json
python scripts/verify_metadata.py docs/generated/metadata.json
python -m mkdocs build --strict
```

`verify_metadata.py` должен проверять наличие commit SHA, dataset version, parameters, timestamp и checksums. Если метаданные не соответствуют коду или отсутствует обязательный output, workflow должен завершиться ошибкой.

## 11. Рекомендуемый конвейер для этого проекта

Для текущего сайта на MkDocs рекомендован гибридный вариант:

1. лёгкие демонстрационные вычисления запускаются в CI;
2. тяжёлые эксперименты запускаются отдельно через `papermill`, batch-систему или notebook-среду;
3. в repository попадают небольшие `results.md`, `results.csv`, figures и `metadata.json`;
4. MkDocs собирает только документацию и проверяет ссылки через `--strict`;
5. GitHub Pages и Helios публикуют один и тот же статический output;
6. каждая страница содержит provenance-блок с версией кода и данных.

Такой конвейер сохраняет простоту текущего сайта и не превращает публикацию в непредсказуемый долгий пересчёт.

## 12. Итог

Граница между стратегиями проходит не по названию инструмента, а по стоимости и требованиям к воспроизводимости вычисления. `nbconvert`, MyST-NB и Quarto удобны, когда notebook можно безопасно выполнять при сборке. `papermill` лучше подходит для параметрических серий, а связка скрипт + `Makefile`/`nox` лучше всего отделяет вычислительный этап от публикационного.

Для коротких, детерминированных и малых экспериментов вычисление в CI даёт максимальную автоматическую проверку. Для тяжёлых или специализированных расчётов следует выполнять эксперимент отдельно, сохранять outputs с commit SHA, версиями данных, параметрами, окружением и checksum, а CI использовать для валидации и публикации готового артефакта.
