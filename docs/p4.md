# P4. Развёртывание на Helios с контролем качества доставки

## Цель ЦЕЛЬ ЦЕЛЬ 

Helios ИТМО используется как второй статический хостинг проекта. Базовый workflow `.github/workflows/helios-static-html.yml` публикует production-версию `main`. Отдельный workflow `.github/workflows/p4-helios.yml` реализует требования P4: собирает MkDocs, передаёт архив по SSH deploy-ключом, публикует его в staging/release-каталог, выполняет healthcheck и сохраняет предыдущую версию.

## Healthcheck

После выкладки workflow запрашивает опубликованный URL через `curl --fail --location`, делает до трёх попыток с таймаутом 30 секунд, проверяет успешный HTTP-ответ и ищет контрольную строку `Исследовательские материалы` в HTML. При недоступности сайта или отсутствии строки job завершается ошибкой.

## Preview-сборки

Для `main` используется основной адрес:

```text
https://se.ifmo.ru/~s506308/project-python/
```

Для любой другой ветки P4 workflow автоматически нормализует имя и публикует сайт отдельно:

```text
https://se.ifmo.ru/~s506308/project-python/previews/<branch>/
```

Например, `feature/results` становится `previews/feature-results`. MkDocs получает соответствующий `SITE_URL`, поэтому внутренние ссылки ведут в правильный подкаталог.

## Резервная копия и откат

Перед заменой target-каталог переносится в:

```text
~/.helios-backups/project-python/<branch>/previous
```

Новая версия сначала распаковывается в staging-каталог и только потом перемещается в публичный путь. При ошибке между заменами shell `trap` возвращает предыдущую директорию.

P4 workflow не запускается автоматически для `main`, чтобы не дублировать базовую публикацию. Production-вариант P4 можно запустить вручную через **Actions → P4 quality deployment to Helios → Run workflow**. Ручной откат выполняется там же с включённым параметром `rollback`: workflow меняет местами текущий каталог и `previous`, а затем повторяет healthcheck.

## Что происходит при обрыве

Если соединение оборвалось во время SCP, публичный target ещё не меняется и старая версия продолжает работать. Если архив уже передан, но распаковка или перемещение staging завершились ошибкой, `trap` возвращает `previous`, когда target уже успел исчезнуть. Если healthcheck не проходит после публикации, workflow красный, а backup остаётся на сервере.

Это не полноценная транзакция файловой системы: внезапное отключение сервера в узком окне между двумя `mv` может потребовать ручного восстановления из backup-хранилища.

## GitHub Pages и Helios

| Критерий | GitHub Pages | Helios |
| --- | --- | --- |
| Время доставки | Сборка, artifact upload и Pages deployment | Сборка, SCP/SSH и HTTP healthcheck |
| Надёжность | Управляемая GitHub deployment API | Зависит от SSH, сервера и места на диске; backup снижает риск |
| Отладка | Логи job и deployment status в GitHub | Логи SSH/SCP и проверка удалённых каталогов |
| Preview-ветки | Требуют отдельной настройки deployment | Естественно размещаются в `previews/<branch>` |
| Откат | Повторный deploy старого commit | Переключение `previous` через workflow |
| Контроль доступности | GitHub отвечает за endpoint после deployment | Явный curl healthcheck встроен в pipeline |

Точные секунды доставки следует измерять по длительности конкретных workflow runs на одинаковом commit и одинаковом артефакте. В отчёте нужно разделять время сборки, передачи, публикации и healthcheck.

## Ограничения

- секрет `HELIOS_SSH_KEY` хранится только в GitHub Secrets;
- пароль Helios не используется workflow и не должен возвращаться в YAML;
- healthcheck проверяет главную контрольную строку, но не каждую ссылку;
- backup хранится на Helios, поэтому нужно следить за квотой диска;
- preview-каталоги удалённых веток требуют отдельной cleanup-процедуры.

## Вывод

P4 превращает SSH-копирование файлов в контролируемую доставку: preview не смешивается с production, HTTP-проверка ловит неполную выкладку, а предыдущая версия сохраняется для отката. GitHub Pages проще в эксплуатации, а Helios даёт больше контроля над каталогами ценой собственной логики резервирования и проверки.
